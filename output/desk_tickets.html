What would have been simpler as one agent

Ticket 102. It is one lease row and one rent pay. A single agent with get_lease + prepare_payment would have staged $2,400 without a Facilities-to-Accounting handoff. The handoff still earned its keep as a role split (space vs cash), but it was the least necessary of the three. 101 is worse as one agent: shelf qty, vendor hold, cash, and a customer draft are four different mistakes waiting to happen. 103 needs both margin math and a shelf count; collapsing those is how you promise 20 hoodies you cannot restock.

Three new problems this team could already solve

  1. Another size of CC-TEE-WHITE goes to 0 while vendor 1 is clean — Inventory get_sku_stock / vendor_can_ship, Accounting stages a reprint against checking, human stamps, receive_stock.
  2. A second rent notice on lease 1 next month — Facilities get_lease, Accounting get_cash + prepare_payment. After this run checking is $160, so the tool would refuse a $2,400 pay and the board would show the shortfall instead of going negative.
  3. Yale AI Club asks for 8 navy M at 10% off — Inventory already knows qty 8, Accounting already knows $52.20 > $22, CS already has the draft language. No new tools.

Three new problems this team could not solve, and what we would need

  1. A customer returns the S tee. Cash only goes out; there is no inbound-cash tool and no return table. We would need a human-approved receive-cash route and a returns agent (or Inventory + Accounting with a restock_from_return tool).
  2. Elm City wants next month’s rent plus a CAM charge that is not on the lease row. get_lease only has monthly_rent. We would need a charges table and a Facilities tool that reads it, plus Accounting that can stage a split pay.
  3. Actually email Tauhid or the club. CS is forbidden from sending. We would need a separate outbound-mail agent with a human “send” stamp, the same way pays work, plus a sent-mail log. The current draft-on-ticket tool is not that.
